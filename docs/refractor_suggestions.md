# Refactoring Suggestions for mfree_iwf_ul_cut_refine Project

This document contains the detailed refactoring analysis and suggestions generated by the refactor-reviewer agent.

## Key Findings
1. **Monolithic Functions**: Several functions exceed 100-200 lines, particularly in `adaptivity.cpp` (e.g., `perform_split_triangular`, `perform_split_cubic_basic`) and `contact.cpp` (e.g., `contact_apply_master_to_body_2d`). These violate the single responsibility principle and are difficult to test and maintain.

2. **God Class Anti-Pattern**: The `particle` class exposes over 50 public data members, mixing concerns like position, velocity, stress tensors, thermal properties, and adaptivity flags. This breaks encapsulation and makes the class hard to evolve.

3. **Global State Issues**: Use of singletons (`simulation_time`) and global variables (`global_logger`) hinders testability and introduces tight coupling.

4. **Monolithic Main Function**: `refine_cut_main.cpp`'s `main()` function spans hundreds of lines, handling argument parsing, environment setup, simulation loop, and output - a clear violation of separation of concerns.

5. **Build Configuration Redundancy**: `CMakeLists.txt` duplicates source file lists for both executables, violating DRY principles and increasing maintenance burden.

6. **Mixed Coding Standards**: Inconsistent use of C-style headers (`<stdio.h>`) versus C++ headers (`<cstdio>`), and presence of commented-out code in constructors.

7. **Poor Directory Organization**: Benchmark/test code is mixed with production source code in `src/benchmarks/`, rather than being separated into a dedicated test directory.

8. **Resource Management Risks**: Raw pointer usage in constructors (e.g., `body` constructor) without clear ownership semantics, and potential for memory leaks with dynamically allocated components.

## Refactoring Suggestions

### 1. Break Down Long Functions
**Priority**: High
**Target Files**: `adaptivity.cpp`, `contact.cpp`
**Strategy**: Extract smaller, focused functions from monolithic methods. For example:
- Split `perform_split_triangular` into `calculate_son_positions()`, `assign_son_properties()`, and `validate_mass_conservation()`
- Decompose `contact_apply_master_to_body_2d` into `detect_contact_events()`, `compute_contact_forces()`, and `apply_friction_model()`

### 2. Encapsulate Particle Data
**Priority**: High
**Target Files**: `particle.h`, `particle.cpp`
**Strategy**:
- Group related data into private member structs (e.g., `struct Position { double x, y; }`, `struct Velocity { double vx, vy; }`)
- Provide public accessor methods and computed properties
- Implement proper copy/move semantics

### 3. Eliminate Global State
**Priority**: Medium
**Target Files**: `simulation_time.h`, `refine_cut_main.cpp`
**Strategy**:
- Pass `simulation_time` as a dependency rather than using singleton pattern
- Inject logger dependency through constructor parameters instead of global variable
- Consider using dependency injection container for better testability

### 4. Modularize Main Function
**Priority**: High
**Target Files**: `refine_cut_main.cpp`
**Strategy**:
- Extract `parse_command_line_args()` function
- Create `setup_simulation_environment()` for environment variable handling
- Implement `run_simulation_loop()` to contain the time-stepping logic
- Separate output handling into dedicated functions

### 5. DRY CMake Configuration
**Priority**: Low
**Target Files**: `CMakeLists.txt`
**Strategy**:
- Define source file lists as variables and reuse them
- Use `target_sources()` for conditional compilation
- Consider separating common sources into a static library

### 6. Standardize Includes and Modernize Code
**Priority**: Low
**Target Files**: All header files
**Strategy**:
- Replace C-style includes with C++ equivalents (`<cstdio>`, `<cmath>`)
- Remove commented-out code and unused includes
- Use `std::array` instead of C-style arrays where appropriate

### 7. Reorganize Directory Structure
**Priority**: Medium
**Target Files**: `src/benchmarks/`
**Strategy**:
- Move benchmark/test code to `tests/` or `benchmarks/` at project root
- Separate unit tests from integration benchmarks
- Use CMake's testing framework more effectively

### 8. Improve Resource Management
**Priority**: Medium
**Target Files**: `body.h`, `body.cpp`
**Strategy**:
- Use smart pointers (`std::unique_ptr`) for owned resources
- Implement proper RAII for dynamically allocated components
- Add move constructors/assignment operators where appropriate

## Benefits
- **Maintainability**: Shorter functions and better encapsulation will make the codebase easier to understand and modify
- **Testability**: Eliminating global state and breaking down large functions enables unit testing of individual components
- **Performance**: Better data locality through encapsulation may improve cache efficiency
- **Reliability**: Proper resource management reduces memory leaks and undefined behavior
- **Scalability**: Modular design allows for easier parallelization and optimization of specific components
- **Developer Productivity**: Clear separation of concerns reduces cognitive load and speeds up development

## Implementation Notes
- Start with high-priority items (function decomposition, encapsulation) as they provide the most immediate benefits
- Consider using modern C++ features (C++17/20) for better expressiveness and safety
- Implement changes incrementally with comprehensive testing to ensure numerical accuracy is maintained
- The custom GLM implementation is adequate but consider migrating to full GLM library for additional features
- Benchmark performance impact of encapsulation changes, as scientific computing often prioritizes data access patterns
- Consider adding static analysis tools (clang-tidy, cppcheck) to prevent regression of code quality issues
